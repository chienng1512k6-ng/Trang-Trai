# FDS-012-FIX-001 — Prevent Safari double-tap zoom on Attack

Priority: P1. Status: **CLOSED — owner confirmed real-iPhone Safari PASS for Attack**.
Owner retest passed center/text double taps, 10 taps, joystick+Attack, outside
release, app switch/return and camera zoom. Parent FDS-012 remains PARTIAL:
non-Attack page zoom was tracked in [FIX-002](./FDS-012-FIX-002.md), now also
owner-verified CLOSED (10/10 iPhone Safari cases). Remaining FDS-012 gates are
independent desktop Chrome functional QA and actual desktop Alt-Tab. A production
benchmark is measured separately in embedded Chromium, not standalone Chrome.
No FDS-013 work, dependency or engine changes.

## Evidence and diagnosis

The owner reproduced page zoom after two rapid Attack taps on real iPhone Safari.
They report joystick, multi-touch, combat, collision, camera, safe areas, app
switch/reload and a 10-minute session otherwise passed. Phone model, iOS/Safari
version and numerical device FPS were not supplied; no values are inferred.

Attack is a DOM `button.touch-action` containing text and a `small` label, outside
the Phaser canvas/camera. Before this fix the button already had `touch-action:
none`, while the child label was independently hit-testable with default `auto`.
Pointerdown on that child bubbled to the button, which called preventDefault and
captured the owning pointer. Pointerup releases only that ID and preserves one
pending press; cancel/lost capture clears an owned pending press. Combat samples
that latch once per frame. No Attack handler calls camera zoom.

This is a browser gesture-policy issue, not the 450 ms combat cooldown or Phaser
camera zoom. Canceling a Pointer Event is not sufficient to suppress browser
viewport gestures. CSS is the primary mechanism, evaluated from the hit-tested
element/ancestors before the gesture. See the
[Pointer Events specification](https://www.w3.org/TR/pointerevents3/).
An ancestor `touch-action:none` should already restrict descendants in compliant
implementations; the child default alone is **not proof of the Safari root cause**.
The precise affected Safari implementation/version is not confirmed locally.
WebKit documents touch-action's role in
[double-tap gesture handling](https://webkit.org/blog/5610/more-responsive-tapping-on-ios/).

## Narrow fix

- Apply explicit `touch-action:none` to Attack and every descendant. Make its
  decorative descendants `pointer-events:none`, so tapping the subtitle hits
  the button itself. Joystick policy and overlay/background policy are unchanged.
- Given the real-device failure despite existing CSS, add an explicitly
  non-passive `touchend` listener **on Attack only**. It calls preventDefault
  only when cancelable, suppressing the touch-end default which can trigger
  Safari's page gesture/click behavior. It does not process attack state, emit
  clicks, stop propagation, inspect timing, debounce or filter pointer IDs.
- Existing pointer capture, pointer ownership, release/cancel, combat cooldown,
  Space/mouse and lifecycle cleanup remain authoritative. The added listener is
  removed during normal destruction, using the same registered options.
- Viewport meta stays `width=device-width, initial-scale=1.0, viewport-fit=cover`.
  No user-scalable=no, maximum-scale cap, global gesture handlers or document-wide
  touch-action restriction. System edge gestures/app switching are not intercepted.
